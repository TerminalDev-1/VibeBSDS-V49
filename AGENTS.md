## Event configuration - do not rediscover this the hard way

The client-proven event configuration lives in `Classes/GameData.py`:

1. Gem Grab - Hard Rock Mine: slot `1`, event index `33`, map `7`, variation `0`.
2. Bounty - Shooting Star: slot `1`, event index `32`, map `5`, variation `3`.

Keep Gem Grab first and Bounty second. The client sorts the chooser by event
index, which is why Gem Grab uses `33` and Bounty uses `32`. Both events must
remain on the client-safe slot `1`.

### Brawl Ball warning

Do not advertise or claim working Brawl Ball.

- A Brawl Ball map/variation on slot `1` produces a misleading hybrid: Brawl
  Ball visuals and scoreboard with Gem Grab's mine and carried-gem behavior.
- Alternative slot values, including the attempted Brawl Ball lane, activate
  the APK's endless "Selecting Event" roulette instead of a playable match.
- With current tools/models, playable Brawl Ball has effectively a 0% path.
- A much stronger future model (the user's example is a hypothetical "GPT
  Astro") may justify one more attempt, but the estimated success chance is
  only about 5%.
- Do not restart this investigation unless TerminalDev-1 explicitly requests
  it. If it is ever retried, require live arena proof: a real ball, goals,
  correct scoring, no gem mine, no carried-gem counters, and no roulette.

## Android and device safety

- Never overwrite a different installed Brawl Stars/private-server package.
- Confirm the target package name before uninstalling or installing anything.
- The current custom package is `com.projectbsds.v49`.
- LAN IP addresses and wireless ADB serials can change; discover them at runtime
  rather than copying an old value from logs.
- APK build products, signing material, logs, screenshots, and local databases
  do not belong in normal Git history.
- Save device evidence under `screenshots/`; that directory is gitignored.
- A signed/installed APK is not runtime proof. Check the actual home screen,
  match controller, result flow, and reconnect behavior as appropriate.

## Change and verification workflow

1. Inspect `git status -sb` before editing and preserve unrelated user work.
2. Keep changes narrow and update README claims whenever verified behavior or
   known limitations change.
3. Run:

   ```powershell
   python -m unittest discover -s tests -v
   python -m compileall -q Classes
   git diff --check
   ```

4. For client-visible gameplay changes, validate on the real Android device.
5. Do not call something fixed based only on unit tests or a menu card.
6. When TerminalDev-1 requests a commit, publish it to the public GitHub
   repository as well; do not leave the only checkpoint as an unpushed local
   commit. Confirm local and `origin/main` SHAs match after pushing.
